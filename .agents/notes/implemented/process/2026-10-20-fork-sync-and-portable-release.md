# Agent Note: 定制版的上游同步与便携测试版发布

Status: implemented

## Problem

本 fork 已包含自有功能，需要持续吸收 AyuGram 上游变更并分发可追溯的 Windows 测试包。现有 Canary 流程依赖上游的运行器、签名与 Telegram 发布设施，不能视为本 fork 已具备的发布能力。[榜单功能笔记](../../implemented/feature/2026-10-19-channel-top-posts.md)中的实机回归说明，编译成功不足以证明功能可用，因此必须区分同步准入与发布准入。

## Decision

目标是供维护者和少数朋友使用的 Windows x64 便携测试版；跟踪 `AyuGram/AyuGramDesktop:dev`，定制开发保留在 `jinmo100/AyuGramDesktop:dev`。首阶段复用 E 盘 Windows 环境，由维护者执行本机发布命令，不引入 self-hosted runner 或云端完整应用构建。

用户已逐项确认设计并授权实施。仓库包含同步工作流、本机发布命令、配置向导及行为测试；外部 GitHub App 安装和首次真实发布仍需实际凭据与干净的 Windows 源码工作区。落地代码不代表远端工作流已启用。

### 上游同步

每天检查一次上游，使用只保存上游历史的 `upstream-sync` 分支并复用一个指向定制 `dev` 的同步 PR。保留普通 merge 历史，不改写定制分支历史。上游重写历史、出现合并冲突或检查失败时停止自动合并，保留 PR 或失败运行供人工处理，通过 GitHub 的通知机制提示。

对候选合并结果执行四类轻量检查：合并无冲突、笔记门禁、工作流语法检查、现有四组独立逻辑测试。测试主要覆盖复制逻辑和模拟对象，不能视作生产代码或 Windows 验证。为检查提供固定版本的工具依赖；笔记归档比较明确使用同步前基线，不能因浅克隆或默认 `HEAD` 跳过比较。

全部通过后自动合并，不等待本机 Windows 结果；用户接受 `dev` 暂时不能编译的可能。验证结果必须绑定确切的目标分支与上游提交，分支发生变化时重新验证。既有 Depot 工作流不应因普通云端 runner 无法识别自定义标签而形成无关的永久阻塞。

门禁及其依赖、测试、配置文件的上游改动一律转人工审查，避免候选自行弱化检查。合并提交由固定父提交和确定时间生成，验证与落盘可重建同一 SHA。最终原子推送同时提供来源和目标 lease；目标变化由服务端拒绝。镜像分支只允许同步机器人写入，同一并发组串行处理；Git 对没有变化的来源 ref 可能省略服务端更新，不能把 lease 当成任意外部写者存在时的跨 ref 读锁。需要人工更新镜像时先暂停工作流。

同步机器人采用只安装到本 fork 的 GitHub App，以短期安装令牌执行操作，按需授予内容、PR 和工作流写入权限。检查任务与写操作分离，检查执行时不暴露机器人私钥或发布凭据。App 的创建和安装需要维护者完成登录授权步骤，不将密钥写入仓库。

### 本机发布

发布命令接收或选定一个已提交并推送的确定提交，复用 E 盘依赖与缓存，重新执行 Windows x64 Debug 增量构建。构建源码或相关子模块存在未提交改动、与指定提交不符时，停止并列出差异，不自动提交、清理或重置。当前遗留的 `prepare.py` 改动必须在第一次发布前明确处理。发布不自动推送尚未推送的功能提交。

发现该构建版本程序仍在运行时，停止并提示维护者退出后重试，不自动关闭。Windows Debug 编译、Qt 布局回归与干净打包校验全部通过，才允许公开发布。实机测试由维护者自行安排，说明中准确标注验证范围。

版本采用上游版本加发行序号，例如 `v7.2.9-jinmo.1`。脚本可计算下一个可用序号，已有 tag 和资产不覆盖；源码固定提交、发布 tag、程序内上游基础版本、Debug 配置与校验值在发布元数据中对应。GitHub 包名和 Release 标识使用 `AyuGram-Jinmo`，首阶段保留程序内原有 AyuGram 名称与图标。

在新暂存目录收集明确的分发文件，包含空的 `TelegramForcePortable`、许可证及说明，不复制使用中的整个构建目录，不带入账号数据、缓存或日志。提供 ZIP、SHA-256 与构建来源信息，并指向对应源码提交。

本机命令完成后直接公开 GitHub Pre-release，不另设人工草稿批准。可用草稿作为上传事务的内部暂存态：所有资产校验上传完成后由命令自动公开；中途失败保持未公开并报告状态，不公开缺件版本。重试先识别同一版本的暂存状态，不覆盖既有公开发行。本机认证使用 GitHub CLI 登录，凭据留在系统凭据存储，不写入脚本或发布包。

### 更新边界

首阶段关闭内置自动更新，朋友从本 fork 的 Releases 手动下载。除禁用更新器外，还需检查并调整应用中的手动下载入口，避免跳转到上游。暂不建设独立更新服务、更新签名信任链或安装器，不调用依赖上游私有签名环境的发布脚本。

## Alternatives considered

自动开 PR、人工合并的优势是允许维护者逐次评估上游行为变化；用户选择轻量检查通过后自动合并，因此仅在异常时回退人工处理。

等待 Windows 编译和真实布局回归后才同步的优势是减少开发分支不可用的概率；用户选择同步只跑轻量检查，将 Windows 验证放在公开测试版的发布门禁。

仅跟上游正式版本的优势是变动频率较低；用户选择跟踪 `dev`，以保持当前基线并及时吸收变更。

云端独立构建的优势是维护者电脑离线也能产包；用户首阶段选择复用已完成的 E 盘依赖，降低建设成本。本机暂不接入 Actions runner。

Release 草稿等待人工公开的优势是有最后一次人工检查；用户选择本机命令通过约定门禁后直接公开 Pre-release，因此草稿只作可恢复的内部暂存态。

细粒度 PAT 的优势是初次配置简单，内置 `GITHUB_TOKEN` 的优势是无需额外凭据；用户选择仓库范围的 GitHub App，接受初次配置成本，以获得短期令牌和所需的工作流更新能力。

## Testing

本轮通过临时真实 Git 仓库和外部 GitHub CLI 替身验证同步与发布行为，包括冲突、改写历史、目标和来源变化、门禁篡改、脏子模块、未推送或错误提交、静态运行库和工具版本、上传失败、草稿重试、已有公开版本及 tag 归属。轻量门禁包含四组既有逻辑测试、固定依赖的笔记门禁与 actionlint。原生 PowerShell AST 解析和独立失败日志测试通过；独立 CMake 配置脚本验证正确 URL 可用、开启更新器或非法 URL 被拒绝。

本轮没有重新构建、启动或关闭完整应用，没有配置远端 Secret、启用远端工作流或实际公开 Release。首次真实运行仍是外部验收前置条件，不能以模拟 API 的成功代替。原生配置证据显示当前 MSVC 使用静态 Debug CRT（/MTd），但干净机器上的第三方运行依赖尚未验证。

- 同步只改约定分支；无更新不制造空 PR，失败不自动猜测冲突解决方式，确切候选提交通过检查后才能合并。
- 每份分发包能追溯到已推送的源码提交与构建配置，包含干净的便携目录，不包含测试账号数据。
- 未提交修改、错误提交、运行中的程序、失败的构建或回归均阻止发布，并给出可操作的原因。
- 上传失败不公开缺件版本，重试不覆盖已公开版本或已有 tag。
- 公开说明明确标注 Debug、已验证范围和手动更新方式，不承诺未验证的网络或长期同步行为。
- 用户最终确认方案后再新增或启用同步、构建及发布自动化。

## Consequences

跟踪开发分支并仅跑轻量同步检查，可能自动纳入不能编译或行为回归的更新；这一风险由发布门禁限制传播，不由同步门禁消除。本机离线时不能产包。Debug 程序较大，程序内基础版本与独立发行序号可能不同，需用发布元数据消除歧义。GitHub 定时任务可能延迟或在长期无活动后停用，通知也受维护者订阅设置影响。签名、独立自动更新和正式安装版留到后续阶段。
